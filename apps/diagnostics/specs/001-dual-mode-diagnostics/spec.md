# Спецификация: две вкладки диагностики VIN

Версия 1.0 · 2026-11-06 · реализация не начата.

## Польза и границы

Диагностика отвечает на два разных вопроса: «может ли телефон выполнить поток камеры и подготовки кадра для серверного VIN-сканера?» и «может ли этот телефон распознать VIN самостоятельно, каким движком и с какой задержкой?». Успешный мок не является успешным OCR. Успешный OCR одного тестового изображения не является доказательством качества на любых автомобилях.

В результате будущей реализации пользователь получает один HTML, открывает его в поддерживаемом браузере, разрешает камеру по кнопке и выбирает один из двух режимов. Фотографии и распознанные значения остаются в памяти. Никаких запросов к BFF, облачным OCR, CDN, аналитике или mock API при работе файла нет. Виртуальная «отправка» первой вкладки и реальные локальные вычисления второй подписаны раздельно.

Реальная авторизация, HTTP-связь с TISS, доступность провайдера, поиск запчастей по VIN, обучение моделей и production-интеграция в B2B вне задачи. Продукт не переезжает на Angular/React и не получает сервер.

## Истории пользователя

| История | Что делает пользователь | Наблюдаемый результат |
|---|---|---|
| US01 | Открывает файл на телефоне | Понимает, выполняется ли JavaScript и доступна ли камера в этом просмотрщике |
| US02 | Запускает вкладку «Браузерный мок» | Видит реальный фрагмент камеры и виртуальный обмен, синтетический итог явно подписан |
| US03 | Выбирает движок на вкладке «На устройстве» | Получает действительное локальное распознавание либо конкретную причину недоступности |
| US04 | Замораживает один фрагмент и переключает движки | Сравнивает результаты на одинаковых пикселях без подмены этого тестом живого потока |
| US05 | Меняет VIN вручную, останавливает или сворачивает страницу | Поздний ответ не перезаписывает ввод; камера и worker прекращают работу |
| US06 | Экспортирует отчёт | Получает факты об устройстве, режимах и ошибках без фотографий и VIN |

## Функциональные требования

| ID | Требование |
|---|---|
| FR01 | Ровно две вкладки верхнего уровня: «Браузерный мок» и «На устройстве». Активна только одна; смена вкладки останавливает предыдущий запуск и ресурсы. |
| FR02 | Проверка среды: статический `noscript`/стартовый fallback, URL-протокол, secure context, JS, необходимые API, браузерные сведения без утверждения точной модели телефона по user agent. |
| FR03 | Камера включается только по пользовательской команде. Предпочитается задняя, после разрешения доступны список и переключение. Показываются фактические settings; отсутствие необязательных полей не является ошибкой. Незавершённое разрешение можно отменить логически. |
| FR04 | Мок/Paddle/Tesseract переиспользуют текущую камеру, playsinline, ROI и JPEG. Полноценный vin-scanner использует штатную камеру и UI; одновременно разрешён один владелец камеры. ROI учитывает cover/поворот. Проверки резкости и возможностей сохраняются отдельно от штатного сканирования. |
| FR05 | Настройки baseline/mock/Paddle/Tesseract и frozen: 750 мс; 30 с; JPEG до 1280 px, качество 0,8, до 1 500 000 байт; применяются к новой попытке. Невалидный/слишком большой JPEG не обрабатывается. Native live форка сохраняет собственный full-frame путь и interval 200 мс, JPEG-бюджет мока к нему не применяется. |
| FR06 | Вкладка мока использует существующие виртуальные config/create/frame/delete. Адреса показаны как текст; запросы никогда не передаются `fetch`, XHR, формой, beacon или WebSocket. Для кадров реально создаются JPEG Blob, UUID, FormData и локальная multipart-сериализация. |
| FR07 | Сохраняются основной сценарий Searching → NeedBetterFrame → Candidate → Recognized и ошибки из `contracts/mock-scenarios.json`: NoVin, таймаут, лимит, выключение, провайдер, шесть HTTP 400, 503, медленный ответ, задержка следующего кадра и попытка продлить дедлайн. Ожидаемая ошибка — успешная проверка обработки, не неисправность устройства. |
| FR08 | В клиентской вкладке есть один select с PaddleOCR, Tesseract.js, vin-scanner (пользовательский форк). Загружается и работает только выбранный движок; до команды запуска камера и OCR не включаются автоматически. |
| FR09 | Все три реализации действительно распознают входные пиксели локально. PaddleOCR: JS + ONNX/WASM; Tesseract: JS + core WASM + eng; форк: полный штатный компонент/worker, YOLO detector + VIN recognizer + n-gram/consensus. Мок ответа вместо движка запрещён. |
| FR10 | Живой режим использует свежие кадры общей ROI. Замороженный режим хранит один неизменяемый фрагмент для последовательного сравнения трёх движков. Синтетические тесты логики и OCR-факты имеют отдельные метки источника. |
| FR11 | Paddle/Tesseract: trim + upper case, один полный 17-символьный кандидат `[A-HJ-NPR-Z0-9]{17}`, без скрытых исправлений/склейки. vin-scanner: полный native алгоритм, beam/n-gram, rescoring, исправления, Tier A/B/C и fallback. Результат форка не проходит дополнительный строгий фильтр. |
| FR12 | Paddle/Tesseract live: два последовательных различных свежих кадра с одинаковым кандидатом; противоречие/отсутствие сбрасывает подтверждение. vin-scanner: native consensus и события без внешнего порога. Frozen/live и число исходных изображений отмечаются, но алгоритм форка не меняется. |
| FR13 | Пользователь может ввести ожидаемый VIN для локальной оценки. Сравниваются точное совпадение и число несовпадающих позиций при равной длине. Confidence сохраняется с исходной шкалой; не называется вероятностью правильного VIN и не используется для рейтинга между движками. Контрольная цифра/WMI — информация, не универсальный запрет. |
| FR14 | Не более одного кадра в обработке, очереди нет. Интервал — минимальный промежуток между стартами, кадр снимается непосредственно перед обработкой; после долгого ответа не воспроизводятся пропущенные тики. Общий дедлайн не продлевается. |
| FR15 | Инициализация OCR ограничена 60 с и отменяема; попытка начинается после готовности движка/камеры. Мок — до виртуального создания сессии. У форка сохраняется native интервал 200 мс, у остальных default 750 мс. Внешний диагностический deadline 30 с показан и не меняет внутренние пороги consensus. |
| FR16 | Стоп, завершение, смена вкладки/движка/камеры, `visibilitychange` hidden и `pagehide` отменяют текущую работу, tracks, worker, таймеры и временные URL. После возврата нет автоматического возобновления. |
| FR17 | Каждый async-результат связан с runId/generation/engineId/frameId. Старый запуск, позднее разрешение камеры, ответ после отмены/дедлайна или смены движка не меняют UI, поле VIN и результат нового запуска. |
| FR18 | У поля VIN есть revision. Любой ручной ввод после старта попытки запрещает последующую автоматическую запись этой попыткой. Разрешённая автоматическая запись выполняется один раз; поиск по VIN не запускается автоматически. |
| FR19 | Отчёт v2 разделяет deviceChecks, logicChecks, engineChecks, runs, events и manualChecks. Доступны копирование с fallback и скачивание JSON. Нет фотографий, бинарных данных, OCR-текста, введённого/распознанного VIN, идентификаторов камер и чувствительных сообщений исключений. |
| FR20 | Результаты: работает / ошибка / заблокировано средой / не проверено / требуется ручная проверка; running только промежуточный статус. Для ограничения указаны операция, фактические данные и причина. Ошибка среды не объявляется отсутствием камеры на телефоне. |
| FR21 | Runtime HTTP(S), WS(S), внешние script/image/worker/font и серверный OCR запрещены. Для встроенных ресурсов допустимы `blob:` и `data:` в узких CSP-директивах. Счётчики виртуальных операций, локальных чтений ресурсов, запрещённых попыток и независимая сетевая проверка различаются. |
| FR22 | Будущий результат выпускается одним HTML со встроенными JS, worker, WASM, моделями и словарями, без CDN/установки на телефоне. Build-time зависимости допустимы с зафиксированными версиями и хешами. Возможность такого выпуска проверяется до основной разработки, не предполагается доказанной. |
| FR23 | Интерфейс русский, mobile-first от 320 CSS px, без горизонтального скролла страницы, с доступными вкладками/кнопками и читаемыми длинными адресами. Поворот не меняет выбранный режим или VIN. |
| FR24 | Показаны версии движка/моделей/профиль; лицензии/NOTICE сохранены. Форк включает n-gram, native shutter/manual burst, guide fallback, torch, autofocus, retry и overlay. Показаны decoder beam/greedy, tier, checkDigitOk, source. Русская локаль добавляется без удаления штатных языков. Все ресурсы имеют проверенные версии/хеши. |

## Критерии приёмки

| ID | Критерий |
|---|---|
| AC01 | На ширине 320/390/768 px доступны обе вкладки, select содержит ровно три требуемых движка, стартовая камера выключена. |
| AC02 | Реальная камера выдаёт кадр; ROI соответствует рамке в portrait/landscape; сформированы JPEG и multipart с достоверными размерами. |
| AC03 | Мок успешно проходит основной сценарий и каждый ожидаемый отказ; виртуальный запрос показан, реальных HTTP(S)/WS(S) запросов при работе нет. |
| AC04 | Каждый движок обрабатывает контролируемый кадр реальным runtime; ответ, метрики и версия показаны. Отсутствующий ресурс даёт явную ошибку без мока или серверного fallback. |
| AC05 | Для одинакового frozenFrameId все три движка получают одни и те же пиксели; отчёт не выдаёт frozen/synthetic за живую камеру. |
| AC06 | Paddle/Tesseract соблюдают строгий формат и подтверждение свежими кадрами. Форк выдаёт те же native решения Tier A/B/C/исправлений/fallback, что pinned исходник на том же входе, без внешнего фильтра или дополнительного голосования. |
| AC07 | Повторные нажатия, отмена ожидания разрешения, переключение, таймаут и поздние ответы не оставляют активную камеру/worker и не меняют новый результат. |
| AC08 | После ручной правки VIN старый запуск не подставляет своё значение. После нового явного запуска применяется новая revision. |
| AC09 | JSON соответствует report-v2.schema.json и не содержит тестовые VIN, OCR-строки, deviceId и изображения, включая events/errors. |
| AC10 | Холодная загрузка, offline-запуск и работа трёх движков подтверждены отдельно на реальных Android Chrome и iPhone Safari либо конкретная комбинация честно отмечена ограничением. |
| AC11 | Читаемость, поворот, сворачивание, блокировка экрана и выключение индикатора камеры проверены вручную. Невыполненные проверки остаются manual/untested. |
| AC12 | Подготовка спецификации не редактирует исходный HTML; baseline сохраняет свой SHA. Внешние обновления учитываются перед реализацией. Регрессии мока проходят без изменения его контракта. |

## Критерий готовности

Готовность означает выполненные задачи T01–T13, подтверждённые AC01–AC12 и честно указанную матрицу поддерживаемых сред. Утверждение «работает на телефонах» без реальных результатов не принимается. Данная версия спецификации не отмечает эти пункты выполненными.
